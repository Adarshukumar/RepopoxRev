# 05 — Network and providers

Sixteen `providers:*` modules, each a thin typed client for one service. They know how to
talk to a service and nothing else — no Android UI, no persistence, no app state. The app
owns all of that.

| module | lines | what it does |
|---|---|---|
| `innertube` | 8,300 | YouTube Music's private API — the primary source |
| `musixmatch` | 754 | lyrics + word-level timing |
| `canvas` | 718 | Apple Music / Monochrome cover art and motion backdrops |
| `shazamkit` | 707 | audio fingerprint recognition |
| `applecanvas` | 564 | Apple Music canvas videos |
| `directlyrics` | 529 | Deezer / NetEase / QQ Music lyrics in one client |
| `betterlyrics` | 494 | TTML (rich timed lyrics) parsing |
| `paxsenixlyrics` | 488 | lyrics API |
| `lrclib` | 422 | open synced-lyrics database |
| `artistvideo` | 260 | artist backdrop videos |
| `kugou` | 250 | Chinese lyrics service |
| `youlyplus` | 240 | lyrics |
| `wikipedia` | 211 | artist biographies |
| `simpmusic` | 193 | lyrics + audio |
| `lastfm` | 173 | scrobbling (Last.fm and Libre.fm) |
| `genius` | 157 | lyrics |

Networking is **Ktor 3.4.0 on an OkHttp engine** with `kotlinx.serialization` JSON, plus
`ktor-client-encoding` and Brotli. Sharing one OkHttp client across the app means the proxy,
DNS and IP-version settings in `utils/AppProxy` apply uniformly — including to third-party
modules, which is why `ModuleHost.http()` is specified as *"HTTP through Mochy's own client,
so its proxy, DNS and IP-version settings apply."*

## InnerTube

`providers/innertube` is the largest non-app module: 105 files, 8,300 lines.

**Ten client identities**, each a `YouTubeClient` with its own `clientName`,
`clientVersion`, `clientId`, user agent and capability flags:

```
WEB, WEB_REMIX, WEB_CREATOR, IOS, MOBILE, ANDROID_NO_SDK,
ANDROID_VR_NO_AUTH, ANDROID_CREATOR, VISIONOS, IPADOS
```

The flags on each are what make this work:

```kotlin
val loginSupported: Boolean = false,
val loginRequired: Boolean = false,
val useSignatureTimestamp: Boolean = false,
val isEmbedded: Boolean = false,
val useWebPoTokens: Boolean = false,
```

Different clients unlock different stream formats and have different attestation
requirements; when one is rate-limited or refuses a format, the service walks to the next.
That walk is the `failedSources` / `resolvedSourceIds` bookkeeping in `MusicService`.

**The public API surface** (`YouTube.kt`, 1,809 lines) covers search, browse, album, artist,
playlist, charts, explore, library, history, player, next, queue, captions, transcript,
lyrics, related, account info, feedback, plus the full write side: like/unlike video and
playlist, subscribe, create/rename/delete playlist, add/remove/move songs, upload a custom
playlist thumbnail, and `registerPlayback` / `reportWatchtime` so plays actually count on the
user's YouTube account.

Pages are parsed into typed models (`pages/AlbumPage.kt`, `ArtistPage.kt`, `HomePage.kt`,
`SearchPage.kt`, `NextPage.kt`, …) rather than leaving raw JSON in the app.

`NetworkConfig.kt` and `models/IpVersion.kt` let the user force IPv4 or IPv6 — a real
practical concern, since YouTube's behaviour differs per stack and per region.

## The three hard client-side problems

There is no server. Everything below happens on the phone.

### 1. PoToken / BotGuard

`utils/potoken/` — `PoTokenGenerator`, `PoTokenWebView`, `JavaScriptUtil`, `PoTokenResult`.

YouTube requires a proof-of-origin token generated by running Google's BotGuard attestation
challenge. The app boots a hidden WebView, loads the attestation JavaScript, and extracts the
token through a `@JavascriptInterface` bridge. `App.kt` explains the scheduling decision:

> Boot BotGuard once a session id exists. Without a PoToken YouTube serves only a ~32 second
> preview window, and paying the engine's cold start inside the playback resolver stalls the
> first track instead.

```kotlin
private const val PoTokenAfterIntroMillis = 2_500L   // after the launch intro, Home's reveal runs ~1s
```

So the WebView is started *after* the splash animation, off the critical path, and only once
`YouTube.visitorData` or `YouTube.dataSyncId` exists (a 60-second bounded wait loop).

### 2. Signature deciphering

`utils/cipher/` — `CipherDeobfuscator`, `CipherWebView`, `PlayerJsFetcher`,
`FunctionNameExtractor`.

YouTube rotates its signature-scrambling function. The app fetches `player.js`, finds the
transform function's name, and executes the deciphering inside a WebView rather than
reimplementing it — so a YouTube-side change does not require an app update.

It caches by player version (`currentPlayerHash`) and retries with freshly-fetched JS on
failure:

```kotlin
suspend fun deobfuscateStreamUrl(signatureCipher: String, videoId: String): String? {
    return try {
        deobfuscateInternal(signatureCipher, videoId, isRetry = false)
    } catch (e: Exception) {
        Timber.tag(TAG).e(e, "Cipher deobfuscation failed, retrying with fresh JS")
        …
    }
}
```

`CipherDeobfuscator.initialize(context)` is called in `App.onCreate()` before anything else
that could need it.

### 3. SABR streaming

`utils/sabr/EjsNTransformSolver` solves the `N`-transform parameter for SABR (streaming
adaptive by request) playback — again by running the solver JavaScript in a WebView with a
`WebChromeClient` capturing `ConsoleMessage` output, bridged back to Kotlin with
`suspendCancellableCoroutine`.

**The pattern across all three is the same and it is the key architectural idea:** rather than
reverse-engineer and reimplement each obfuscated algorithm — which breaks every time YouTube
ships a change — execute YouTube's own JavaScript in a sandboxed WebView and bridge the result
back. Fragile, but self-updating. The `assets/solver/` directory ships the harness for it.

`NewPipeExtractor` (`v0.25.2`, from JitPack) is also available and `YouTube.getNewPipeStreamUrls()`
offers an alternative resolution path; `settings.gradle.kts` even has a commented-out
`includeBuild("../NewPipeExtractor")` with dependency substitution for developing against a
local extractor checkout.

## Lyrics — twelve sources, ordered and fallible

`lyrics/LyricsProviderRegistry.kt` is the aggregator. A stable map of built-in providers:

```kotlin
"YouLyPlus", "Paxsenix", "BetterLyrics", "SimpMusic", "LrcLib", "Kugou",
"NetEase", "QQMusic", "Deezer", "YouTubeSubtitle", "YouTubeMusic", "YouTubeCaptions"
```

plus runtime-registered module providers:

```kotlin
@Volatile
private var moduleProviders: Map<String, ModuleLyricsProvider> = emptyMap()
val providerNames: List<String> get() = moduleProviders.keys.toList() + providerMap.keys
```

The interface is minimal and `Result`-based, so one provider failing is normal operation:

```kotlin
interface LyricsProvider {
    val name: String
    fun isEnabled(context: Context): Boolean
    suspend fun getLyrics(id, title, artist, duration, album): Result<String>
    suspend fun getAllLyrics(…, callback: (String) -> Unit) { … }   // default: first success
}
```

Three design details worth stealing:

**The default order encodes domain knowledge**, and the comment says so:

> NetEase, QQ Music and KuGou near the end: they are Chinese services, and LyricsHelper only
> believes them first-hand for Chinese songs. NetEase leads them because it often has word
> timing. YouTube's auto captions last of all — they are speech recognition.

**Newly-enabled modules go first**, because that is why the user enabled them:

```kotlin
val newModules = moduleProviders.keys.filter { it !in saved }
return newModules + saved + getDefaultProviderOrder().filter { it !in saved && it !in newModules }
```

**A saved order never goes stale.** `deserializeProviderOrder` tolerates providers added after
the order was saved, appending them in default order rather than dropping them.

Beyond fetching, `lyrics/` does real signal processing: `AudioFingerprint` + `Fft` +
`VocalActivity` for fingerprinting, `LyricsAutoSync` and `LyricsAligner` to align unsynced
lyrics to audio, `CaptionAligner` for captions, `VideoAudioSync` / `VideoLyricsSync` to align
lyrics against the music video, `GoogleTranslateEngine` and `YouTubeCaptionTranslation` for
translation, and `EmbeddedLyrics` / `EmbeddedLyricsFile` to read lyrics out of local files.
`AudioMatcherTest`, `LyricsAutoSyncTest`, `CaptionAlignerTest` and `LyricsUtilsTest` cover the
parts that are pure enough to test — a sensible split.

## Scrobbling

`scrobble/` with `providers/lastfm`. Both Last.fm and Libre.fm are supported, and the build
script's MD5 stand-in for missing Libre.fm keys (see [02](02-build-system.md)) means the
feature survives a fork with no secrets configured. `ScrobbleTimer` in `MusicService` gates
submissions on actual listen time.

## The module system

`modules/api/MochyModule.kt` is the contract — deliberately **free of Android imports** so a
module packaged as its own APK can be loaded at runtime. Its header comment states the rule:

> what mochy and its modules agree on, kept free of android so a module app loads at runtime;
> change a shape and bump the version (docs/notes/modules.md)

```kotlin
const val MODULE_API_VERSION = 3
```

One interface, three optional capability mixins:

```kotlin
enum class ModuleFeature { AudioSource, Lyrics, Look }

interface MochyModule { val info; val adds: Set<ModuleFeature>; fun attach(host: ModuleHost); … }
interface SourceModule  : MochyModule   // suspend fun resolve(track, picks): ResolveResult
interface LyricsModule  : MochyModule   // suspend fun lyrics(track): String?
interface LookModule    : MochyModule   // val look: Map<String, String>
interface ServerListModule : MochyModule // user-addable servers
interface ItemListModule   : MochyModule // user-addable zips/links (scripts, packs)
```

The host surface is deliberately tiny — `storage`, `http`, `log`, `folder` — so a module gets
no access to the database, the player, accounts or the filesystem at large.

**The security model is the interesting part**, and `modules/README.md` states it plainly:

> Nothing from a look, a web module or a plain zip runs inside Mochy. They only hand back JSON,
> stream links and look values, so anyone can make one and nobody has to be trusted with the
> app. Code that runs inside Mochy (a zip with its own code, built-in modules and module apps)
> is only loaded when it's signed with Mochy's own key.

So there are three trust tiers: data-only modules (untrusted, anyone can write one),
JavaScript scripts (sandboxed inside the JS Modules module, internet-only), and native code
(signature-checked).

**`LookModule` is capability-limited by construction.** A theme module can only set keys in
the `LookSetting` allowlist — `playerStyle`, `homeStyle`, `blurStrengthPx`, `accentColor`,
`ipodWheelColor` and fifteen others — *"so a module can restyle mochy but never touch
accounts, network or playback."* Anything else in the map is ignored.

`ResolveResult` is a sealed interface with `Found` / `NotFound` / `Unavailable`, so "the
service doesn't have this song" and "the service couldn't be asked" are distinguishable, and
the provider walk can make different decisions for each. `SourceStream` carries `codec` and
`sampleRateHz` so the player can skip a stream the device cannot decode, and `StreamDrm.Widevine`
supports DRM sources with a `LicenseServer` callback invoked on the player's DRM thread.

Built-in modules: `applemusic` (795 lines), `monochrome` (630, FLAC), `jiosaavn` (335).
`modules/bridge` (1,008 lines) loads external ones; `modules/local`, `modules/web`,
`modules/skin` and `modules/code` implement the four module kinds.

One loose end: `modules/catalog.json` — the list behind Settings → Modules → "Find more
sources" — is **empty** (`"modules": []`), and it points at `docs/notes/modules.md`, which is
`.gitignore`d and absent. So the discovery surface ships inert.
